# laya-rocm benchmarks

Laya on an AMD Radeon 8060S (Ryzen AI Max+ 395, gfx1151) through ROCm on WSL2. Every configuration ran in a fresh process. Latency is wall-clock `predict()` time after warm-up, synchronised with the GPU. Generated by `bench/make_report.py` from `results/`.

## What the numbers say

- **Laya runs on ROCm and the answers are right.** GPU BF16 matches a CPU FP32 run of the same checkpoint on 99.15% of typed-decisions top-1 answers, and GPU FP32 reproduces it exactly. The CPU reference itself reproduces upstream's published T4 accuracy (0.3615 vs 0.3620), so this harness measures what upstream measured.
- **The GPU, not Python, is the limit.** Only 13% of a single-question call happens outside the forward pass, and throughput saturates near 110 questions/s (16q x 64 tok). Little is left to win on the host side; GEMM efficiency is the lever.
- **FP16 is the accuracy choice, not the speed choice.** It tracks the FP32 reference far better than BF16 does: top-1 agreement 0.9990 vs 0.9915, 0 vs 2 flips at the 0.85 confidence threshold, p99 |dp| 0.0025 vs 0.0151. It is not faster -- paired, it is 4% slower at 10 questions and no measurable difference at 50. BF16's wider exponent buys nothing for this model while its shorter mantissa costs precision, so FP16 is the better trade wherever a confidence threshold drives a decision. It is **not** the default -- one GPU is not evidence for every GPU -- so pass `dtype="fp16"`.
- **TunableOp: no measurable difference at one question, 5% faster at fifty -- and it has to be paid for.** The first tuning pass, with nothing cached, took about an hour: it benchmarks kernel candidates for every new GEMM shape the workload produces. A later pass reusing that CSV took 9 minutes. Tuning must be repeated per GPU and after ROCm/PyTorch upgrades, and the CSV is not portable. Worth it for a long-lived service on stable shapes, not for a short job.
- **rocBLAS instead of the default hipBLASLt: no measurable difference.** A single early run suggested a large rocBLAS win on one workload; the paired runs do not support it. Measure your own shapes before switching.
- **Upstream `laya` on the same GPU measures 6% slower than `laya_rocm`** (paired, and the same at 1 and 10 questions). Caching the tokenized question head removes host-side work, which is real but small beside the forward pass -- only 13% of a one-question call is host-side to begin with. The package's value is that it *runs* and picks sane precision, not that it makes the GPU faster.
- **The multilingual checkpoint is about twice as fast as the English one** (16.1 vs 35.5 ms at one question) because it is a smaller model (322M vs 421M parameters). It also ships uncalibrated, so its confidences deserve less trust -- upstream's finding, unrelated to ROCm.
- **`predict_many` wins only a little on this GPU** (up to x1.33, and noisy) because a single call already saturates it. It helps more on the smaller multilingual checkpoint, which does not.
- **Without a C compiler, stock `laya` cannot complete a GPU forward pass on torch 2.13 + ROCm at all** -- a Triton kernel in `torch._native` JIT-builds a C stub. `laya_rocm` detects this and routes those ops to the stock kernels. That is a correctness fix, not a speed one.

## How much of this is noise

This GPU shares its power and thermal budget with the CPU, and its clocks move with the machine's state. The **same unchanged configuration**, run at different points across one afternoon, measured:

| questions / call | p50 ms across identical runs | spread |
|---:|---|---:|
| 1 | 33.5, 35.5, 42.9 | **28%** |
| 10 | 134.4, 137.1, 147.7 | **10%** |
| 50 | 726.7, 729.7, 796.8 | **10%** |

Single-question latency is the worst case: between calls the GPU goes idle and clocks down, so the measurement reflects how fast it ramps back up. Sustained batches hold their clocks and are steadier.

**Consequence: any wall-clock difference below roughly 10-20% here is noise, not a result.** The absolute latency tables below were recorded across several hours and should be read with that in mind. Differences between configurations come from the paired runs instead.

## Caveats

- WSL2 runs are reported to reach roughly 70–80% of native Linux throughput; ROCm profilers are unavailable in WSL and pinned host memory is disabled.
- The 8060S is an iGPU: its memory is carved out of system RAM, and CPU load competes for the same bandwidth.
- Without a C compiler, torch 2.13's Triton-backed `torch._native` ops are switched off (stock kernels are used) and `torch.compile` is unavailable. This applies to upstream `laya` as well: on this stack it otherwise fails its first GPU forward pass.
- The T4 rows are upstream's published numbers (torch 2.11 + CUDA 12.8), not re-measured here.
